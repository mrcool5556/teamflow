1 · First-time setup · /setup

A guided setup for the person installing the server

Shown only while the server has no accounts at all. Step 1 creates the admin account and signs them in. From then on /setup is shut for everyone else: the server refuses a second admin account and the web app sends /setup to the login page. Steps 2–5 are ordinary admin settings shown to that admin as a wizard. They can leave half-way, and the checklist on the admin Overview picks up where they stopped.

  • Works with only the secrets in .env. The site address is filled in from the page the installer opened, and nothing needs a restart.
  • A value set in .env wins and shows as "Set in .env" (read-only), so production's current setup keeps working unchanged.
  • "Skip for now" on Email. Without email, password resets go through an admin. The checklist says so.

Q1 · Who may claim a brand-new server?

A. Whoever opens it first. This is what happens today: the first account to register becomes admin.

B. Whoever has the one-time setup code. The installer prints it and it is in the server log; the Installs lane would show it with the setup link.

B. A fresh server on a public address can be claimed by a stranger in the minutes before you open it. The code costs one paste.

Q2 · Should .env still win over the page?

PUBLIC_URL, SMTP_* and TEAMFLOW_INVITE_ONLY exist today.

Yes, while they are set. The field shows "Set in .env" and can't be edited. Production keeps working unchanged, and new installs leave them empty.

Q3 · Does "Flow" reach the admin page too?

A. Flow everywhere. The admin page says Flows, Free Flow and Admin Flow.

B. Flow for members; the admin page keeps "Spaces" as the storage view of the same thing.

A. Two names for one row is what confuses people. "Free Flow · 1 GB" reads fine.

Q4 · Capital F?

"Create a Flow" vs "Create a flow".

Capital F, as a product name ("a Flow", "your Flows"). It also keeps it apart from the ordinary word "flow".

Build plan · after George picks Q1–Q4

Numbered steps, one commit each

  1. Settings in the database. New instance_settings keys: site (name, address), mail (SMTP, password encrypted), signup, setup (checklist dismissed). Values set in .env win. Move every reader of config.publicUrl, config.smtp and config.inviteOnly (CORS, mail, Discord, health check) to getters that pick up changes without a restart. M · no schema change needed: the table exists
  2. Setup API. Public GET /setup/status → { needed } (true only with zero accounts). POST /setup/admin creates the account in one transaction that re-checks for zero accounts; afterwards it always returns 409. Setup code if Q1 = B. Rate-limited like login. M · tests: second call refused, refused once any account exists, race of two calls
  3. Admin settings API. GET/PATCH /instance/site, /instance/mail (+ POST …/test), sign-up on /instance/settings, GET /instance/setup-checklist. M
  4. /setup in the web app. Five steps, desktop rail and phone progress bar, address prefilled from the page. The login page sends you to /setup while it's needed; /setup sends you to login once it isn't. L
  5. Sign-up makes no team. Register creates only the account. With an invite it joins that team. The first account (admin) gets an admin Flow through "Create my first Flow". M · biggest test churn (fake API, server tests that expect GEN)
  6. /welcome, Create a Flow, Join a Flow. Zero-Flow users are routed here. Create uses POST /teams, with the "first one is never refused" rule kept. Join uses extractInviteToken + GET /invites/:token preview + accept. L
  7. Admin page: checklist card, "Site & email", "People", sign-up switch. People: list, make or remove admin (never the last one), send a reset link. L
  8. "Flow" wording pass per the table (after Q3/Q4). Text only, plus tests that match on text. M
  9. Hand-off to the Install lane: installers print the setup link (and code), and leave PUBLIC_URL/SMTP out of the generated .env. S · their lane
  10. Docs: new docs/SETUP.md, SPACES.md ("Flows"), API.md (pnpm docs:api), README first-run section. S

Risks

  • Takeover of a fresh server before its owner opens it (Q1). The setup code removes it; without it, keep the window short.
  • Dropping the automatic "General" team touches many tests and anything that assumes every user has a team (MCP and CLI defaults, the board shell). Existing users and teams are not changed.
  • Address and email moving from .env to the page: CORS, mail and the Discord bot read them at boot today, so a missed reader keeps the old value. Step 1 lists every reader and adds a test for each.
  • SMTP password in the database is encrypted with the secrets key, but it does end up in DB backups (encrypted). Changing the key means re-entering it.
  • Address prefill behind a proxy shows http:// unless TEAMFLOW_TRUST_PROXY is on. It's editable, and the reachability check catches it.
  • Production is unaffected by setup (it has accounts), but plan step 5 changes sign-up there too: new users get the welcome screen instead of General.
  • Settings → Updates is not touched (Install lane).

# Self-hosting Teamflow

Teamflow runs on your hardware. **Teammates only need a browser**: they open your address and accept an invite. This guide is for the person who runs the server.

## Pick a setup

| Setup | Best for | Install | Update |
|-------|----------|---------|--------|
| **[A. Windows](#setup-a-windows)** | A PC at home or in the office | The Teamflow app, or one PowerShell line | Settings → Updates |
| **[B. Linux / Proxmox](#setup-b-linux-or-proxmox)** | An always-on server | One line on the Proxmox host, or one line on Debian/Ubuntu | Settings → Updates or `sudo update` |

Every setup runs the same prebuilt release from [GitHub Releases](https://github.com/mrcool5556/teamflow/releases): one Node 20 process, SQLite in `data/teamflow.db`, files in `data/uploads/`, API and web UI on port **3000**. Nothing is built on your machine and no git checkout is needed. Docker is an [optional appendix](#appendix-docker-optional).

```text
You (host)                                  Teammates
──────────                                  ──────────
run the installer → open the setup link →   https://your-address
Settings → Updates when a new version shows    refresh the browser
```

Every release lists `SHA256SUMS` and has a GitHub build attestation; the installers check the checksum of everything they download. How releases are made: [RELEASING.md](RELEASING.md).

## Production checklist

The installers do items 1–3 and 7 for you. Check the rest on every production install:

1. **Node 20.** The Linux installer installs it from NodeSource; on Windows Teamflow keeps its own copy in `<install folder>\node\`. `better-sqlite3` is built for Node 20 only.
2. **`JWT_SECRET`**: generated by the installers (64 hex characters). The server **refuses to start** while it is unset, short, or a shipped placeholder (`change-me-...`, `dev-secret`).
3. **`TEAMFLOW_SECRETS_KEY`**: generated too; encrypts Discord secrets at rest. On an existing install without it, the installer leaves it unset: the server then keeps using `JWT_SECRET`, which encrypted the saved secrets, so they stay readable. Don't add a new key to such an install.
4. **Public address**: the address users open, e.g. `https://tasks.example.com`. Used for invite and reset links and as the allowed browser origin. Set it in setup step 2 or on Server admin → Site & email (no restart); `PUBLIC_URL` in `.env` still works and then wins.
5. **`CORS_ORIGINS`**: only if the web UI is served from a different origin than `PUBLIC_URL` (comma-separated). Default is same-origin only.
6. **Behind a reverse proxy:** `TEAMFLOW_TRUST_PROXY=1`, so login rate limiting sees real client IPs.
7. **Setup B:** in-app updates need the sudoers rule from `setup-maintenance-sudo.sh`. The installer runs it and stops if it fails.
8. **Admin account:** there is **no demo user**. On a fresh install, open the setup link the installer prints (`/setup?code=…`, see [SETUP.md](SETUP.md)) and create the **instance admin** account there (the **Server admin** page in the account menu, Updates, Discord bot secrets and service, Flows). Ordinary sign-up opens after that. On an upgraded install the oldest account is promoted once. To grant more, use Server admin → People, or set `TEAMFLOW_INSTANCE_ADMINS=you@example.com,other@example.com` (applied at their next login).
9. **Trash purge:** issues in the trash are not purged at boot. Set `TEAMFLOW_DB_MAINTENANCE_NIGHTLY=true` (03:00 server time), or see [DEPLOYMENT.md](DEPLOYMENT.md#schema-patches-and-data-maintenance).
10. **Email** for password reset: setup step 3 or Server admin → Site & email (with a test send), or `SMTP_*` in `.env`. Without it, an admin hands out reset links from Server admin → People.
11. **`.env` permissions** on Linux: `chmod 600`, owned by `teamflow` (the installer sets this).
12. **Disk and spaces:** keep more than **2 GB** free on the disk that holds `data/uploads/`; below that every upload in every space is refused until room is made (`TEAMFLOW_MIN_FREE_DISK_BYTES`, `0` turns the floor off). Each user may create up to 3 free spaces with 1 GB of uploads each; their own **General** counts. Review these in Server admin → Space defaults ([SPACES.md](SPACES.md)).

Invite-only sign-up is a switch in setup step 4 and on Server admin → Flow defaults & sign-up (`TEAMFLOW_INVITE_ONLY=true` still works).

**How `.env` is read.** At startup the server loads `TEAMFLOW_ENV_FILE` if set, else `.env` in the install folder. Variables already in the process environment always win over the file. The installers write only the port, database path and secrets; site name, address, email and sign-up live on the Server admin page.

### Remote access

```text
Browser → Caddy / Cloudflare / Tailscale → Teamflow :3000
```

## Setup A: Windows

**Good for:** a PC that is on while your team works. Windows 10 or 11, x64 (no ARM build). Under 1 GB of disk for Teamflow, plus your data, plus the 2 GB free-disk floor for uploads. Nothing else to install first.

### Option 1: the Teamflow app (easiest)

1. Download `TeamflowSetup-vX.Y.Z.exe` from the [latest release](https://github.com/mrcool5556/teamflow/releases/latest).
2. Run it. The installer is not code-signed yet, so Windows SmartScreen says **"Windows protected your PC"**: click **More info**, check that the publisher line says *Unknown publisher* and the file name is `TeamflowSetup-…exe`, then **Run anyway**. (Compare the file with `SHA256SUMS` on the release page if you want to be sure: `Get-FileHash .\TeamflowSetup-v0.2.0.exe`.)
3. It installs for your Windows user (no admin needed) and opens Teamflow on the setup page. Create the admin account there.

The app lives in the tray (the notification area by the clock). Closing the window keeps the server running; the tray menu has **Open**, **Open in browser**, the address for other PCs on your network, **Start with Windows** (on by default), **Open data folder** and **Quit**. Quit stops the server; teammates can't reach Teamflow until you start the app again.

Data is in `%LOCALAPPDATA%\Teamflow` (`.env`, `data\`, `backups\`). Uninstalling the app (Windows Settings → Apps) leaves that folder in place.

### Option 2: one PowerShell line

For a server that runs without anyone signed in, or if you prefer no app. In PowerShell:

```powershell
irm https://github.com/mrcool5556/teamflow/releases/latest/download/install.ps1 | iex
```

- **Not elevated:** installs to `%LOCALAPPDATA%\Teamflow`, adds a Start-menu shortcut and starts Teamflow when you sign in.
- **Run as administrator:** installs to `%ProgramData%\Teamflow` and offers the **Teamflow** Windows service (NSSM, installed with winget if missing), so it runs at boot without a signed-in user, and a firewall rule for port 3000 (default no).

It downloads its own Node 20 from nodejs.org (checked against nodejs.org's `SHASUMS256.txt`) whatever Node the PC already has, downloads and checks the release, writes `.env` with new secrets, sets up the database, starts Teamflow, waits until it answers and opens the setup link. It prints the link too.

Options go after the script when you run it this way:

```powershell
& ([scriptblock]::Create((irm https://github.com/mrcool5556/teamflow/releases/latest/download/install.ps1))) -Service -Port 8080
```

`-Version X.Y.Z`, `-Port N`, `-InstallDir <folder>`, `-Service` / `-NoService`, `-Firewall`, `-NoBrowser`, `-Update`, `-Yes`, and `-DryRun` (check the PC and print what would be done, change nothing). Each also reads an environment variable (`TEAMFLOW_VERSION`, `TEAMFLOW_PORT`, …), listed at the top of [install.ps1](../deploy/install/install.ps1).

**Coming from a git checkout** (the old `deploy\windows\install.ps1`): run the line with `-From D:\teamflow`. It copies `.env`, the database and uploads into the new install folder and leaves the old folder alone; stop the old server first.

### Update

**Settings → Updates** shows when a new release is out; **Update now** downloads it, backs up the database, switches over and restarts in about a minute. If the new version doesn't start, Teamflow goes back to the previous one by itself.

From PowerShell instead:

```powershell
& "$env:LOCALAPPDATA\Teamflow\current\deploy\windows\update.ps1"     # or %ProgramData%\Teamflow for the service install
```

More (backups, restore, NSSM, logs): [deploy/windows/README.md](../deploy/windows/README.md)

## Setup B: Linux or Proxmox

**Good for:** a dedicated always-on server. x64 only.

### On Proxmox VE: one line on the host

In the Proxmox web UI open **your node → Shell** (or SSH to the host as root) and run:

```bash
bash -c "$(curl -fsSL https://github.com/mrcool5556/teamflow/releases/latest/download/proxmox.sh)"
```

It asks a few questions (Enter keeps each default: next free ID, hostname `teamflow`, the first storage that holds containers, 8 GB disk, 1 GB RAM, 2 cores, `vmbr0`, DHCP), downloads the Debian 12 template if needed, creates an unprivileged container with nesting, starts it, runs the Linux installer inside and prints the address and setup link. `--yes` takes all the defaults; `--dry-run` only prints what it would do. Options go after a `_` placeholder, for example `bash -c "$(curl -fsSL …/proxmox.sh)" _ --yes --memory 2048`, or as environment variables (`TEAMFLOW_MEMORY=2048`). All options: `--help`, or the top of [proxmox.sh](../deploy/install/proxmox.sh). Doing it by hand instead: [create-lxc.md](../deploy/proxmox-lxc/create-lxc.md).

### On Debian 12+ or Ubuntu 22.04+ (container, VM or bare metal)

As root, or with sudo:

```bash
curl -fsSL https://github.com/mrcool5556/teamflow/releases/latest/download/install.sh | sudo bash
```

It installs what is missing (`curl`, `sudo`, Node 20 from NodeSource), creates the `teamflow` user, downloads and checks the release into `/opt/teamflow`, writes `/opt/teamflow/.env` with new secrets, sets up the database, the systemd service and the in-app update permission, waits for `/health` and prints the address and the one-time setup link:

```text
 Teamflow is running. Finish setup in your browser:

   http://192.168.1.50:3000/setup?code=K7QM-2XPA
   Setup code: K7QM-2XPA
```

Open it, create the admin account and follow the setup steps ([SETUP.md](SETUP.md)). Lost the link? The code is in `/opt/teamflow/data/setup-code` and the service log (`journalctl -u teamflow | grep "Setup code"`).

Options (after `sudo bash -s --` when piped, or as environment variables): `--yes` (`TEAMFLOW_YES=1`), `--version X.Y.Z`, `--port N`, `--update`, `--dry-run`. Re-running it is safe: it keeps `.env`, the database and uploads and only adds what is missing.

**Coming from a git checkout** (`/opt/teamflow` with a `.git` folder, the old install): the installer offers to switch. It backs up the database, moves the checkout aside to `/opt/teamflow.git-<date>`, keeps `.env`, `data/` and uploads, and installs the release in its place. The systemd unit and the `sudo update` command keep working.

### Layout

```text
/opt/teamflow/
  .env                  settings and secrets (kept)
  data/                 database, uploads, maintenance.log (kept)
  releases/v0.2.0/      unpacked releases (the newest two are kept)
  current -> releases/v0.2.0
  apps, deploy -> current/…   so older paths and the systemd unit stay valid
/var/backups/teamflow/  database backups (the newest 10)
```

### SMTP (password reset emails)

Simplest: Server admin → Site & email (or setup step 3) with **Send a test to me**; no restart. Or from the shell, which writes `SMTP_*` into `.env` and restarts the service:

```bash
sudo teamflow-smtp
```

Use your provider's SMTP (no mail server is installed):

| Provider | SMTP host | Port |
|----------|-----------|------|
| Gmail (app password) | `smtp.gmail.com` | 587 |
| Outlook / Microsoft 365 | `smtp.office365.com` | 587 |
| SendGrid | `smtp.sendgrid.net` | 587 |

A value in `.env` wins over the page. Without email, an admin sends reset links from Server admin → People.

### Update

**Settings → Updates** (instance admins) shows when a release is out and updates in about a minute: download and check, database backup, migrations, switch, restart, health check. A failed migration or a release that doesn't answer rolls back to the previous release and database by itself.

From the shell:

```bash
sudo update            # same as sudo teamflow-update; --help lists the options
```

`--version X.Y.Z`, `--channel prerelease`, `--backup-full` (uploads too), `--reinstall`. Progress is logged to `/opt/teamflow/data/maintenance.log`. More, including restore and troubleshooting: [deploy/proxmox-lxc/README.md](../deploy/proxmox-lxc/README.md)

## Inviting teammates

1. Log in on your public address (not localhost).
2. **Settings → Flow → Invite link** → create a link (pick a role; you cannot invite above your own role).
3. Send the link. They register and land straight on that Flow's board. Someone who signs up without a link gets the welcome page, where **Join a Flow** takes a pasted link or code.

## Password reset

**Forgot password?** on the login screen:

- With email set up → the reset link is emailed.
- Without email → a server admin opens Server admin → People → **Send reset link** and passes the link on (it is also logged when `NODE_ENV=development`).

A reset signs the user out everywhere. Details: [AUTH.md](AUTH.md#forgot-password)

## Environment variables

Full list with comments: root [`.env.example`](../.env.example). The ones a production install usually has:

| Variable | Set by | Purpose |
|----------|--------|---------|
| `JWT_SECRET` | installer | Signs sessions; placeholders refused |
| `TEAMFLOW_SECRETS_KEY` | installer | Encrypts Discord secrets; falls back to `JWT_SECRET` |
| `PORT` / `HOST` | installer | Default `3000` / `0.0.0.0` |
| `DATABASE_URL` | installer | `file:./data/teamflow.db` (relative to the install folder) |
| `SERVE_WEB` | installer | Serve the web UI from the API port; `WEB_DIST` moves the build folder |
| `TEAMFLOW_MAINTENANCE_ENABLED` | installer | Turns on Settings → Updates and backups from the app |
| `TEAMFLOW_SETUP_CODE` | you, optional | Choose the first-start setup code instead of a generated one ([SETUP.md](SETUP.md)) |
| `PUBLIC_URL` | you, optional | Links in invites and emails; allowed CORS origin. Usually set on Server admin → Site & email instead |
| `TEAMFLOW_SITE_NAME` | you, optional | Name on the login page, browser tab and emails (default Teamflow). Can be set on the admin page instead |
| `TEAMFLOW_UPDATE_CHECK` | you, optional | `false` stops the six-hourly check for new releases on GitHub |
| `TEAMFLOW_RELEASE_REPO` | leave unset | Where releases come from (default `mrcool5556/teamflow`) |
| `TEAMFLOW_ENV_FILE` | no | Load this env file instead of `<install folder>/.env` |
| `TEAMFLOW_ALLOW_DEV_SECRET` | never in production | `1` accepts a placeholder secret, like `NODE_ENV=development` |
| `CORS_ORIGINS` | no | Extra allowed browser origins |
| `TEAMFLOW_TRUST_PROXY` | behind a proxy | Use `X-Forwarded-For` for rate limiting |
| `TEAMFLOW_AUTH_RATE_LIMIT` | no | Login/register/forgot attempts per minute per IP (default 10) |
| `TEAMFLOW_INSTANCE_ADMINS` | no | Emails that get the instance-admin flag at login |
| `TEAMFLOW_INVITE_ONLY` | no | `true` = registration only through an invite. Can be set on the admin page instead |
| `TEAMFLOW_BACKUP_DIR` | no | Backup folder (Linux `/var/backups/teamflow`, Windows `<install folder>\backups`) |
| `TEAMFLOW_BACKUP_SCRIPT`, `TEAMFLOW_UPDATE_SCRIPT`, `TEAMFLOW_DISCORD_BOT_SCRIPT` | leave unset | Defaults are the root-owned copies sudoers allows (Linux) or the release's own scripts (Windows) |
| `TEAMFLOW_BUNDLE_MAX_ENTRIES`, `TEAMFLOW_BUNDLE_MAX_BYTES` | no | Team bundle import caps (5000 entries, 2 GB) |
| `TEAMFLOW_DB_MAINTENANCE_NIGHTLY` | no | Nightly trash purge and data upkeep |
| `TEAMFLOW_BOT_CONFIG_KEY` | Discord bot | Generated when bot credentials are saved |
| `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `SMTP_USER`, `SMTP_PASS`, `SMTP_FROM` | no | Outgoing email (password resets). Can be set on the admin page instead |
| `ATTACHMENT_MAX_*`, `UPLOAD_CHUNK_*`, `UPLOAD_DIR` | no | See [ATTACHMENTS.md](ATTACHMENTS.md) |
| `TEAMFLOW_FREE_SPACE_CAP_BYTES`, `TEAMFLOW_FREE_SPACES_PER_USER`, `TEAMFLOW_MIN_FREE_DISK_BYTES` | no | Free-space cap (1 GB), free spaces per user (3), free-disk floor (2 GB). See [SPACES.md](SPACES.md) |
| `NODE_ENV` | Linux installer | `production` drops the localhost dev origins; `development` allows a dev secret |

Invalid values (e.g. `PORT=abc`) stop the server at start with a list of problems.

The site name, public address, email and sign-up policy can also be set on the server admin page (stored in the database, used at once, no restart). A value set in `.env` always wins: the admin page shows it as "Set in .env" and won't change it. Leave them out of `.env` to manage them from the page.

Discord bot and MCP have their own docs: [discord-bot.md](discord-bot.md), [MCP.md](MCP.md).

## Moving your board to another machine

1. On the old machine take a backup (Settings → Updates → Advanced → Back up database now, and copy `data/uploads/`; or `sudo teamflow-backup` / `backup.ps1`) and stop Teamflow.
2. Install Teamflow on the new machine with the installer, then stop it.
3. Copy over `.env` (keep the same `JWT_SECRET` / `TEAMFLOW_SECRETS_KEY`, or saved Discord secrets become unreadable), `data/teamflow.db` (and `-wal` / `-shm` if present) and `data/uploads/`.
4. Start Teamflow again.

Linux and Windows installs use the same files, so a board moves between them too. A single team can also move as a bundle: Settings → Team → Export & import (`team.data.transfer`, Owner by default).

## Quick reference

| Action | Windows (A) | Linux / Proxmox (B) |
|--------|-------------|---------------------|
| Install | Teamflow app, or `irm …/install.ps1 \| iex` | `proxmox.sh` on the host, or `curl …/install.sh \| sudo bash` |
| Start / stop | The app (tray → Quit), the **Teamflow** service, or `current\deploy\windows\start.ps1` / `stop.ps1` | `systemctl start teamflow` / `stop` |
| Update | Settings → Updates, or `current\deploy\windows\update.ps1` | Settings → Updates, or `sudo update` |
| Backup | Settings → Updates → Advanced, or `current\deploy\windows\backup.ps1` (to `backups\`) | Settings → Updates → Advanced, or `sudo teamflow-backup` (to `/var/backups/teamflow`; `--db-only`) |
| Restore | Settings → Updates → Advanced → Restore…, or `restore.ps1 --file <name>` | Same page, or `sudo teamflow-restore --file <name>` |
| Logs | `data\logs\` (app and service), `data\maintenance.log` | `journalctl -u teamflow -f`, `data/maintenance.log` |
| Config | `.env` in the install folder | `/opt/teamflow/.env` |

## Appendix: Docker (optional)

Not one of the supported setups; use it only if you already run Docker.

```bash
git clone https://github.com/mrcool5556/teamflow.git
cd teamflow/deploy/docker
cp .env.example .env
nano .env   # JWT_SECRET (real value), PUBLIC_URL
docker compose up -d --build
```

Keep `PORT=3000` in `deploy/docker/.env`: the same file sets the host port and the port the server listens on inside the container, so another value breaks the mapping. To publish on another host port, edit the left side of `ports:` in `docker-compose.yml` instead.

The entrypoint runs migrations (and the demo seed only with `TEAMFLOW_SEED_DEMO=1`) on each start; data stays in the `teamflow-data` volume. Update with `git pull` then `docker compose up -d --build`. In-app updates and the Discord bot service do not work in Docker. More: [deploy/docker/README.md](../deploy/docker/README.md)
